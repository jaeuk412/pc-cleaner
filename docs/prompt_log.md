# LLM 활용 기록 (Prompt Log)

이 문서는 LLM 코딩 에이전트(**Claude Code**, 모델: Claude Opus 5.5)를 사용해
「PC 용량 확보 및 백업 자동화 도구」를 개발한 과정을 기록합니다.
각 항목은 **핵심 프롬프트 → LLM이 한 일 → 문제점과 해결**의 순서로 정리합니다.

## 핵심 프롬프트

| # | 프롬프트 | 결과 |
|---|---|---|
| 1 | "PC 정리 백업"에 대한 프로젝트 분석 | 과제 요건 정리, 주제의 위험 요소와 대책, LLM 활용 방식 결정 |
| 2 | 개발하면서 prompt_log.md로 저장하면서 개발 진행 | 설계, 구현, 디버깅, 테스트, CI, README, 이 기록 문서 |
| 3 | 발표자료 수정 가능하게 ppt로 작성 | 편집 가능한 9장 PPTX와 생성 스크립트 |

## 1단계. 프로젝트 분석

### 핵심 프롬프트 1
> "PC 정리 백업"에 대한 프로젝트 분석

- **과제 요건 정리:** info.txt를 읽고 제출 요건(공개 저장소, 샘플 데이터, requirements.txt,
  발표 자료 5~10장, README에 핵심 프롬프트 기록)을 체크리스트로 정리했습니다.
  예시 주제들과 비교했을 때, 실제 장비(PyVISA)나 API 키(Gmail, Slack)가 필요한 주제보다
  **채점자가 바로 실행해 볼 수 있다(재현성)**는 점이 이 주제의 장점이었습니다.
- **위험 요소와 대책**
  - 채점자 PC에서 파일이 실제로 지워질 수 있음 → **dry-run 기본값과 격리 폴더 이동**
  - 테스트할 샘플 폴더가 필요함 → **샘플 데이터 생성 스크립트**
  - 클라우드 백업은 인증이 필요함 → 로컬 경로 백업을 기본으로 하고, OneDrive나 Google Drive **동기화 폴더를 대상으로 지정**하면 API 없이도 클라우드 백업이 됨
- **LLM 활용 방식 결정:** 과제의 "LLM 활용"은 프로그램 안에 모델을 넣는 것이 아니라
  **코딩 에이전트를 개발 도구로 쓰는 것**입니다. 완성된 프로그램은 순수 Python으로 동작해야
  채점자가 API 키 없이 실행할 수 있습니다. 대신 프롬프트와 디버깅 과정을 기록하기로 했습니다(이 문서를 만든 이유).

### 핵심 프롬프트 2
> 개발하면서 prompt_log.md로 저장하면서 개발 진행

- 아래 2단계(설계)와 3단계(구현과 디버깅)가 이 프롬프트로 진행된 과정입니다.

## 2단계. 설계

LLM이 제안하고 내가 채택한 설계 원칙:

| 원칙 | 내용 |
|---|---|
| 안전 우선 | `clean`은 기본이 **dry-run**. `--apply`를 붙여야 실행되고, 실행해도 삭제가 아니라 **격리 폴더로 이동** |
| 되돌리기 | 이동한 파일 목록을 JSON manifest로 저장하고 `undo`로 원위치 복구 |
| 의존성 최소화 | 핵심 기능은 표준 라이브러리만 사용(`os`, `hashlib`, `zipfile`, `argparse`). 테스트용 `pytest`만 추가 |
| 재현성 | `tools/make_sample_data.py`로 중복, 대용량, 오래된 임시 파일이 들어 있는 샘플 폴더를 생성 |
| 시각화 | 외부 차트 라이브러리 없이 **SVG 막대 그래프가 포함된 HTML 리포트** 생성 |

모듈 구조:

```
pccleaner/
  scanner.py      폴더 순회, 확장자/폴더별 용량 집계
  duplicates.py   크기 → 앞부분 해시 → 전체 SHA-256 3단계 중복 탐지
  temp_finder.py  패턴 + 경과 일수로 오래된 임시 파일 탐지
  cleaner.py      정리 계획, 격리 이동, undo, purge
  backup.py       날짜별 zip 백업, 무결성 검사, 보관 개수 제한
  report.py       HTML 리포트
  cli.py          명령행 인터페이스
```

## 3단계. 구현과 디버깅

실제 개발 중에 발생하거나 발견한 문제와 해결 과정입니다.

### 문제 1. `python` 명령이 실행되지 않음 (환경 문제)
- **증상:** `python --version`이 버전 대신 `Python`만 출력하고 종료 코드 49를 반환했습니다.
- **원인:** Windows의 `python.exe`는 Microsoft Store 설치를 안내하는 **바로가기(App Execution Alias)**였습니다.
  실제 Python 3.13은 `py` 런처로만 실행되었습니다.
- **해결:** `py -3.13 -m venv .venv`로 프로젝트 전용 가상환경을 만들고, 이후에는 `.venv\Scripts\python.exe`를 사용했습니다.

### 문제 2. 임시 폴더 판정 오류: 모든 파일이 'Temp 폴더 안'으로 잡힘
- **발견:** LLM이 코드를 작성한 직후 스스로 검토하는 과정에서 발견했습니다.
- **원인:** `__pycache__`, `temp` 같은 폴더 이름을 **절대 경로 전체**에서 찾았습니다.
  스캔 루트가 `C:\Users\...\AppData\Local\Temp\...` 아래에 있으면 일반 문서까지 전부 임시 파일로 판정됩니다.
  pytest의 임시 폴더도 이 경로 아래에 만들어지므로 테스트 환경에서도 실제로 발생하는 문제였습니다.
- **해결:** 스캔 루트 기준 **상대 경로**에서만 검사하도록 `root` 인자를 추가했습니다.
- **재발 방지:** `test_temp_dir_check_uses_relative_path` 테스트를 추가했습니다.

### 문제 3. 샘플 생성 스크립트가 다른 폴더를 지울 위험
- **원인:** 처음 작성한 코드는 `--out` 폴더가 있으면 `shutil.rmtree`로 통째로 지웠습니다.
  사용자가 실수로 `--out C:\Users\나\Documents`를 입력하면 문서 폴더가 삭제됩니다.
  파일을 안전하게 다루는 도구를 만들면서 테스트 도구가 더 위험한 모순이었습니다.
- **해결:** 스크립트가 만든 폴더에만 표식 파일 `.pccleaner_sample`을 남기고,
  표식이 있거나 빈 폴더일 때만 다시 생성합니다. 그 밖의 경우에는 중단합니다.
- **재발 방지:** `test_sample_generator_refuses_non_sample_folder` 테스트를 추가했습니다.

### 문제 4. Git은 파일 수정 날짜를 보존하지 않음
- **원인:** "60일 지난 .tmp 파일" 같은 샘플을 저장소에 그대로 올려도,
  다른 사람이 clone하면 수정 날짜가 clone한 시각으로 바뀌어 임시 파일 탐지가 0개가 됩니다.
- **해결:** 샘플 파일을 직접 커밋하지 않고 `tools/make_sample_data.py`가 `os.utime`으로 날짜를 지정해 생성하도록 했습니다.
  seed를 고정해 항상 같은 결과가 나옵니다(파일 26개, 20.7 MB, 확보 가능 10.9 MB).

### 문제 5. 격리 폴더로 옮겨도 용량이 늘지 않음 (설계 문제)
- **원인:** 같은 드라이브 안에서 이동하는 것은 이름만 바뀌는 것이라 디스크 여유 공간은 그대로입니다.
- **해결:** 안전을 위해 이동 방식은 유지하고, 확인 후 실제로 비우는 `purge` 명령을 추가했습니다
  (`--yes` 없이는 목록만 표시, `--older-than 14`로 오래된 격리분 일괄 삭제).

### 문제 6. 백업 폴더가 원본 폴더 안에 있을 때 자기 자신을 압축
- **원인:** `backup work --dest work/backups`처럼 지정하면 이전 백업 zip까지 다시 압축되어 백업이 계속 커집니다.
- **해결:** 압축할 때 대상 폴더를 제외하고, 작성 중인 파일은 `.partial` 이름으로 만들었다가
  CRC 검사(`testzip`)를 통과한 뒤에만 정식 이름으로 바꿉니다. 중간에 실패해도 깨진 zip이 남지 않습니다.
- **재발 방지:** `test_backup_dest_inside_source` 테스트를 추가했습니다.

### 문제 7. 정리 직전에 파일이 바뀐 경우
- 스캔과 실행 사이에 파일이 수정되거나 중복 원본이 지워지면 잘못된 파일을 옮길 수 있습니다.
- 실행 직전에 크기와 수정 시간을 다시 확인하고, 중복의 경우 **원본이 아직 있는지** 확인한 뒤에만 이동합니다.
- `undo`도 원래 위치에 같은 이름의 새 파일이 있으면 덮어쓰지 않고 건너뜁니다.

### 문제 8. 린트 오류 (ruff E501)
- HTML/CSS 템플릿 문자열이 한 줄 130자를 넘어 9건이 발생했습니다.
  템플릿은 줄을 나누면 오히려 읽기 어려워서 `report.py`에만 E501 예외를 적용했습니다.

### 문제 9. 공개 리포트에 PC 사용자 이름이 노출됨
- **발견:** 결과물을 사람이 검토하다가 발견했고, 표시 경로를 `jaeuk/`로 바꾸도록 요청했습니다.
- **원인:** HTML 리포트 상단에 스캔 대상의 절대 경로(`C:\Users\<사용자명>\...`)를 그대로 표시했습니다.
  공개 저장소에 올릴 캡처에 PC 계정 이름이 드러납니다.
- **해결:** `scan --display-root jaeuk/sample_data`처럼 리포트에 표시할 경로를 지정하는 옵션을 추가했습니다.
  옵션이 없으면 홈 폴더를 `~`로 가립니다. 테스트에 "실제 경로가 HTML에 없는지" 검사를 추가하고 캡처를 다시 만들었습니다.
- **배운 점:** 기능 버그가 아니어도 **공유되는 결과물의 개인정보**는 사람이 검토해야 하는 부분이었습니다.

## 4단계. 발표 자료 제작

### 핵심 프롬프트 3
> 발표자료 수정 가능하게 ppt로 작성

- **첫 시도:** 개발 PC에 PowerPoint와 LibreOffice가 없어 LLM이 처음에는 HTML 슬라이드를 PDF로 출력했습니다.
  화면 확인은 쉬웠지만 PowerPoint에서 수정할 수 없어서 PPTX로 다시 만들었습니다.
  이때 고친 내용(한글 단어 잘림, 아직 실행하지 않은 CI를 "검증"처럼 표기한 것 정정)은 PPTX에도 반영했습니다.
- **방법:** `docs/slides/build_pptx.py`가 python-pptx로 PPTX를 만듭니다. 모든 글자는 일반 텍스트 상자이고,
  표지의 원형 그래프는 PowerPoint 기본 차트라서 값과 색을 PowerPoint에서 바로 바꿀 수 있습니다. 슬라이드마다 발표자 노트도 넣었습니다.
- **문제:** PowerPoint나 LibreOffice가 없어 결과 화면을 볼 수 없었습니다.
  → 같은 슬라이드 정의로 **PNG 미리보기를 함께 그리는 렌더러**를 만들었습니다(`--preview`).
  실제 맑은 고딕 글꼴로 줄바꿈을 계산해 **글자가 상자를 넘치면 경고**하도록 했습니다.
- **미리보기로 찾아 고친 것**
  - 텍스트 상자 높이 부족 5건(큰 숫자, 소제목) → 높이 조정
  - ✓ 글머리 기호가 빈 네모로 표시됨: Arial에는 ✓ 글리프가 없음 → Segoe UI Symbol 글꼴로 변경
  - 아이콘 뒤가 검은 사각형으로 보임 → 미리보기에서 투명도를 빼먹은 렌더러 버그(PPTX에는 영향 없음)
- **파일 검증:** OOXML 스키마 검사기가 처음에는 모든 파일에서 실패했습니다.
  원인은 덱이 아니라 Windows 경로 길이 제한 때문에 검사기가 스키마 파일을 읽지 못한 것이었고,
  짧은 경로로 옮겨 실행하자 **All validations PASSED**가 나왔습니다.
- HTML/PDF 버전은 PPTX와 내용이 갈라지지 않도록 삭제했습니다.

## 5단계. GitHub 업로드

핵심 프롬프트를 3개로 정리한 뒤, 제출용 공개 저장소에 올렸습니다.
저장소: https://github.com/jaeuk412/pc-cleaner

| 순서 | 한 일 | 문제와 해결 |
|---|---|---|
| 1. 환경 확인 | `git --version` 2.51 확인 | git 작성자 정보가 설정되어 있지 않았고 GitHub CLI(`gh`)도 없었음 → 작성자 정보를 사람이 정해 알려 주고, 저장소는 GitHub 웹에서 직접 생성 |
| 2. 저장소 초기화 | `git init -b main`, 올라갈 파일 목록과 크기 검토, 공개 파일에 PC 사용자명이 없는지 `git grep`으로 확인 | PyCharm 설정 폴더 `.idea/`가 포함됨 → 개인 환경 설정이라 `.gitignore`에 추가하고 제외 |
| 3. 작성자 설정 | `git config user.name / user.email` | PC 전체 설정(`--global`)이 아니라 **이 저장소에만** 설정 |
| 4. 첫 커밋 | 파일 32개 커밋 | PowerShell here-string으로 여러 줄 메시지를 넘기자 git이 메시지를 파일 이름으로 해석해 실패 → 메시지를 파일로 저장하고 `git commit -F`로 해결 |
| 5. 원격 확인 | `git remote add origin ...`, `git ls-remote`로 저장소가 존재하고 비어 있는지 확인 | 빈 저장소여야 README·.gitignore 충돌이 없음 |
| 6. push | `git push -u origin main` | 에이전트의 셸은 비대화형이라 GitHub 로그인 창을 띄우지 못해 실패(`Cannot prompt because user interactivity has been disabled`) → 앱의 터미널 탭에서 다시 실행하고, 브라우저 인증은 **사람이 직접 승인** |
| 7. 확인 | GitHub API로 원격 커밋이 로컬과 같은지, 저장소가 **Public**인지 확인 | 비공개면 과제가 미제출 처리될 수 있으므로 공개 여부를 꼭 확인 |
| 8. CI | push와 동시에 GitHub Actions가 자동 실행 | 결과: lint와 테스트 4개 환경(Ubuntu·Windows × Python 3.10·3.13) **모두 통과** |

- **배운 점:** 로그인, 저장소 생성, 공개 범위처럼 **계정과 권한이 걸린 단계는 사람이 직접** 하고,
  LLM은 명령 실행과 결과 검증을 맡는 방식이 안전했습니다.

## 보완. README "테스트 실행" 설명 명확화

- **프롬프트:** "실행에서 python -m pytest -v 는 어떻게 사용해?" → "환경설정 테스트인 거야? 테스트 실행이라고만 써져 있어서 다른 테스트인 줄" → "확인하는 기능이랑 테스트 예시 넣어서 분명하게 알려 줘."
- **문제:** README에 "테스트 실행"이라고만 적혀 있어 읽는 사람이 환경설정 점검 테스트로 오해할 수 있었음.
- **해결:** 제목을 "기능 테스트 실행 (pytest 13개)"로 바꾸고, 기능별로 어떤 테스트가 무엇을 확인하는지 표로 정리. 임시 폴더에서만 실행되어 실제 파일을 건드리지 않는다는 점과, Store 바로가기 `python` 대신 `.venv\Scripts\python.exe`를 쓰는 방법도 함께 적음.
- **추가 프롬프트:** "그럼 실행환경설정 이후에 순번으로 와야 하는 거 아니야?"
- **해결:** 테스트 설명이 샘플 실습 ⑥ 뒤에 번호 없이 붙어 있어 실습 단계처럼 보였음 → "3. 실행 환경 설정" 바로 다음의 **"4. 기능 테스트 실행"** 섹션으로 옮기고 이후 섹션 번호를 하나씩 조정(설치 → 테스트로 확인 → 샘플 실습 순서).
